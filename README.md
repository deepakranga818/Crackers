# Diwali crackers catalogue

React + TypeScript + Vite for the owner's office/locality group. The authoritative source is the [Google Sheet](https://docs.google.com/spreadsheets/d/1T21rN-iyxcuJyIyYxU-ARjhnqwDrMSRVWH8Z_wWpI2E/edit?gid=1949134617), including prices, products, images and offers. All 46 product rows are retained; both POP-UP entries have separate stable IDs. Prices use integer paise. No backend, payment collection, login, analytics, service worker or fabricated stock.

**Default: friends-and-family list, search indexing discouraged. A product can be ordered only when it has a seller-confirmed selling unit and a reviewed product type, so until the owner confirms units the site is browse-only.** At the time of writing 0 of 46 products have a confirmed unit. The list is not access-controlled: the URL is reachable by anyone who has it, and `noindex`/`robots.txt` only ask search engines not to list it. A public launch needs `"audience": "public"` plus every item in `source/verification.json` verified. Public catalogue publication is unverified separately from ordering. Do not publish just because checkout controls are hidden. See [launch checklist](docs/LAUNCH.md).

## Local setup

Install Node 24 and Python 3.12+. From the repository root:

```powershell
python -m pip install -r requirements.txt
npm ci
npm run import
npm run dev
```

Open the printed localhost URL. `npm run dev`, `npm run dev:demo` and `npm run build` fetch and validate the latest Google Sheet first. New or changed photos are downloaded; unchanged local images are reused. Build then typechecks and writes `dist/`. `npm run preview` serves that build locally.

### Tests

UI tests are deterministic: they run against the committed `src/products.json` snapshot with no Sheet fetch and no network. Live Sheet verification is separate.

- `npm test`: unit tests (pricing, offers, orderability, cart restore, buyer, WhatsApp message, publication gate).
- `npx playwright install chromium`, then `npm run test:browser`: browser tests against four local servers that Playwright starts itself, recording results in `reports/browser-results.json`:
  - **5175** the production configuration and real product data (no confirmed units, so browse-only).
  - **5174** `--mode demo`: public-style fixtures with invented test units and a test pickup location.
  - **5176** `--mode private-fixture`: the production private-list configuration with test-only confirmed units, generated by `tests/fixtures/make-fixture.mjs` from the snapshot. It is flagged on screen and never part of a production build.
  - **5180** `--mode checkout-demo`: the local checkout demo (sample units, fulfilment and a dry-run handoff), generated by `demo/make-demo-data.mjs`. Playwright reuses it if `npm run demo` is already running.
- `npm run test:layout`: measures where products land at 360×800, 390×844, 768×1024, 1366×768 and 640×450 (200% zoom equivalent) and asserts the numeric targets. `LAYOUT_PHASE=before` records a baseline without asserting. Results merge into `reports/layout-metrics.json`; screenshots go to `reports/redesign/{before,after}/`.
- `tests/browser/a11y.spec.ts`: axe (WCAG 2.2 A/AA, including colour contrast) on the catalogue, details, cart and review at phone and desktop sizes, plus keyboard, focus and 44px touch-target checks.
- `npm run test:live`: re-syncs the Google Sheet, runs the Python import test and fails if the committed snapshot is stale. CI runs this as a separate job from the UI tests.

To try **cart → buyer details → review → handoff** by hand, use the local checkout demo: `npm run demo` (or `npm run demo:lan` for a phone on the same network). It runs on its own port (5180), is labelled "Local checkout demo — test data" on every screen, and its handoff is a **dry run** that shows the WhatsApp link and message instead of opening WhatsApp. The actual catalogue is `npm run build:offline` then `npm run preview` (port 4173). Commands, the demo's contents and a manual checklist are in [docs/LOCAL_REVIEW.md](docs/LOCAL_REVIEW.md).

`npm run dev:demo` is the older localhost-only fixture (invented units, test pickup). Unlike `npm run demo`, its handoff really opens WhatsApp, so do not press Continue to WhatsApp there. All of these fixtures are not claims about the seller, and none can be built into a deployable bundle (`vite.config.ts` refuses to build the test modes; `npm test` scans `dist/` for demo and fixture code). Browser tests intercept `window.open`; no WhatsApp message is sent. The `private-fixture` and `checkout-demo` modes are Vite aliases that swap the product data only in those modes.

## Source and updates

- `scripts/sync_google_sheet.py`: read-only export of the supplied Sheet/gid; inaccessible or unsupported data fails sync without silently using old prices.
- `source/google-sheet.csv` and `source/google-sheet-meta.json`: cached snapshot, source URL, fetched time, contact, source hash and offer tiers.
- `source/Diwali_Cracker.xlsx`: historical input, no longer used by normal builds. Explicit historical import remains available.
- `source/category-map.json`: explicit mapping for every source product number, expected name and original category; source mismatches fail the build. Five composite types (dc-029, 030, 031, 037, 038) are kept under the shopper-facing category "More products"; their id stays `review` and the original category stays visible in details. They cannot be ordered until the seller confirms their type.
- `source/product-overrides.json`: seller-confirmed units, availability, enabled flag, quantity limits and verified specifications keyed by stable ID. Do not infer these from price, names or blank Order cells.
- `source/image-manifest.json` and `source/image-provenance.json`: local assets and their exact source URLs; changed links cannot silently reuse an old photo.
- `src/business.ts`: brand, contacts, launch gates, permitted fulfilment, charges, tax, policies, sound and SEO.
- `src/pricing.ts`: shared exact paise calculations and orderability checks.
- `src/cart.ts`, `buyer.ts`, `whatsapp.ts`, `audio.ts`: isolated state and validation.
- `reports/import-report.md`, `reports/image-report.md`: reproducible audits. `reports/image-quality.md` (from `python scripts/image_quality.py`) lists photos that the card frame cannot make look good.

Update the Google Sheet, then run `npm run sync` to refresh the running local preview, or restart it. Hosted static sites need a fresh build and redeployment; editing the Sheet alone does not instantly update an existing deployment. Do not edit cached CSV/generated JSON as a competing source. Inspect reports and diffs. New IDs or changed names/categories need category-map review; valid prices update directly. Removed products disappear. Invalid rows remain represented/disabled and fail the build. Never reuse a source No. for a different product.

`npm run build:offline` explicitly builds the last fetched Sheet snapshot for local work; it does not claim latest data.

## Sheet offers

The owner confirmed one discount on the whole product subtotal: 10% through ₹2,000 inclusive; 15% above ₹2,000 through ₹5,000 inclusive; 20% above ₹5,000. The matching Sheet coupon (currently CRACK10, CRACK15 or CRACK20) applies automatically without a separate entry field and appears in checkout and WhatsApp. The percentages, codes and boundaries come from the Sheet, and integer-paise rounding occurs once on the total discount. Cart, checkout and WhatsApp use the same calculation. Supported updated offer lines are imported; ambiguous/unsupported text blocks sync for review. The shopper-facing wording is derived from the same tiers the calculation uses (`offerSummary` in `src/pricing.ts`), so there is no gap between ₹2,000 and ₹2,001: 10% when the product total is ₹2,000 or less, 15% when it is above ₹2,000 and up to ₹5,000, 20% when it is above ₹5,000. The tier is chosen from the product subtotal in paise before any fulfilment charge or tax.

**Reference prices are hidden.** Columns are matched by header name, including MRP, and the importer keeps `mrpPaise`. But every Sheet MRP is exactly 1.4× the selling price (`node scripts/mrp-ratio.mjs` prints the evidence), which looks formula-derived, and nothing records the owner confirming them as genuine reference prices. Until `referencePrices` in `source/publication-approval.json` is set to `{"confirmed": true, "reference": "<where the owner confirmed it>"}`, cards and details show the selling price only: no struck-through MRP, no "% off" and no savings. The publication gate rejects `confirmed: true` without a reference.

Example override, only after actual seller verification:

```json
{"dc-001":{"sellingUnit":"<actual confirmed unit>","availability":"available","enabled":true,"maxQuantityPerRequest":20,"stockQuantity":null,"verifiedSpecifications":[]}}
```

Source pack text is descriptive evidence only; it does not establish the selling unit. Limits are request limits, not stock. **A product with no confirmed selling unit, or an unreviewed product type, cannot be added, restored into an orderable cart or handed off to WhatsApp, on the private list as well as in public mode.** Nothing assigns "per item" as a default. `unavailable` blocks everywhere. On the private list, unknown availability does not block, because the seller confirms stock on WhatsApp for every order; a public shop additionally requires availability to be recorded as `available`. The owner edits source/configuration and redeploys; there is no fake static admin panel.

## Product images and licences

All 51 source screenshot-page URLs now resolve to real product photographs on Lightshot's current `img.lightshot.app` image host. They have been downloaded and optimized as local WebP assets for 44 products, with multi-image galleries where supplied. `60 Shot` and `100 Shot` have no source photographs and keep the fallback. See the image report. Public reuse rights still require owner verification before publication. Source screenshot links never become runtime image URLs.

`python scripts/resolve_images.py` audits linked pages without downloading image files. `python scripts/resolve_images.py --download-supplied-images` retrieves the workbook-linked assets for an authorized local build. Use `--rights-confirmed` only when the owner has actually confirmed publication reuse rights for all linked assets. The resolver permits reviewed origins only, reports inaccessible/unapproved links, limits download size and never bypasses access controls. If a host changes, manually review before editing the allowlist. Run the importer after updating assets.

The diya/firework SVG and placeholders are original decorative code; they do not depict product packaging. Audio is original Web Audio synthesis (sine tones), with no recordings or external licences. System fonts avoid third-party font requests. No real product-image licence has been established. React, Vite and other dependencies retain their own licences in installed packages/lockfile.

## Cart and handoff semantics

The cart badge counts units. Local storage stores schema, catalogue version, product IDs and quantities only. Current prices are always used; a catalogue version change triggers a review notice. Removed/disabled items and malformed quantities are removed; an item whose selling unit, product type or availability no longer allows ordering is kept but flagged with a reason and Remove action, and checkout stays blocked until it is removed. Unavailable storage falls back to memory. Storage events update other tabs without writing back.

Buyer details are in React memory only. Returning to the cart preserves the form; Reset buyer details clears it. Refreshing the page intentionally discards buyer details. A reviewed request reference persists in memory for an unchanged request, changes on material edits, and resets on clear/refresh. User fields are flattened to a single line and rendered as text. All optional blank lines are omitted. Totals are shared between cart and request; no GST is assumed.

The buyer stage of the same drawer (no extra page) shows a **Review your request** block above the button: every item with its variant, unit, quantity, price and line amount, the offer, subtotal, fulfilment charge ("Seller will confirm" when unknown), and the buyer's name, mobile and fulfilment, with Edit items and Edit details actions. "View the complete WhatsApp message" shows the exact text that will open, once the form is valid. The concise message contains name/mobile, every product/category/quantity/line amount, subtotal, the Sheet offer and amount. Internal IDs, catalogue versions, timestamps and dummy pickup details are omitted. The buyer must tap Send in WhatsApp; availability and fulfilment still need seller confirmation. Cart is retained.

Below the configurable 4,000-character encoded URL threshold, the full order is prefilled. Longer orders get a small copy/download panel inside the same form; copying or manual attachment acknowledgement is required before opening the reference-only chat link. Paste/attach all details and tap Send there. Nothing is truncated; edits invalidate prepared text. Clipboard failure exposes selectable complete text. No universal device URL limit is claimed.

Mobile checkout includes a fixed cart/subtotal bar, full-height cart and buyer views, large touch buttons, 16px form fields to avoid mobile auto-zoom, and a single-column catalogue on very narrow screens. Safe-area padding and content space keep the cart bar from covering the end of the page.

## Layout and accessibility

Styles are mobile-first with design tokens in `src/styles.css` and breakpoints at 761px, 1051px and 1500px. Fonts are system fonts only (the CSP and the no-third-party-requests rule). The shop bar (search and categories) is sticky; the header is sticky from 761px up. `useStickyOffset` (`src/components.tsx`) measures the real height of the pinned UI, sets `--sticky-h`, applies it as `scroll-margin-top` on controls and anchors, and switches stickiness off when the stack would take more than 30% of the screen (20% on phone-width layouts), such as at 200% zoom or on a landscape phone. Reference prices, units and offers follow the rules above; the sound toggle is opt-in.
